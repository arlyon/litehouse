# Research open event-rule and state-transition standards

Type: research
Mode: AFK
Status: resolved
Resolved: 2026-07-15
Blocked by: None
Map: [Find the route to Litehouse's first connected release](../map.md)

## Question

Which existing open standards or well-formed languages can represent IFTTT-style
event-condition-action automations as a reviewable pre-state to planned post-
state transition, project naturally into a React Flow graph, compile to a small
bounded Rust/Wasm interpreter, and still preserve typed Litehouse capabilities,
quantities, explicit time, receipts, and ambiguous real-world effects? Compare
at least W3C RIF-PRD, Reaction RuleML, OMG DMN/FEEL, W3C SCXML, CNCF Serverless
Workflow, CloudEvents filtering/subscriptions, IEC function-block precedents,
and relevant pure transformation languages such as CEL, jq/jaq, Rego, or
Starlark. Determine whether Litehouse should adopt a standard directly, use a
strict profile, compose standards, or retain a minimal owned IR.

## Decision

**Retain a minimal, versioned Litehouse graph/transition IR and compose standards at its boundaries.** The recommended composition is:

1. **CloudEvents 1.0.2** for event envelopes at ingress, egress, and receipt boundaries, not as the rule language. CloudEvents standardizes event context and transport-neutral formatting, while deliberately leaving event data opaque ([CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)).
2. **A strict CEL profile** for pure conditions and small derived values. CEL is side-effect-free, terminating, mutation-free, gradually type-checkable, and designed for typed host-provided variables/functions; its canonical checked AST is Protocol Buffers ([CEL overview](https://github.com/cel-expr/cel-spec/blob/master/README.md), [language definition](https://github.com/cel-expr/cel-spec/blob/master/doc/langdef.md), [introduction/type checking](https://github.com/cel-expr/cel-spec/blob/master/doc/intro.md)). Do not expose arbitrary extension functions: expose only deterministic Litehouse functions selected by exact-major capability contracts.
3. **An owned, typed plan value** as the only result of evaluation: `pre_state + event + clock_snapshot -> desired_state_patch + effect_intents + diagnostics`. Represent generic JSON state changes with **JSON Patch** operations, including `test` preconditions, but wrap device effects in typed Litehouse intent records rather than pretending physical effects are JSON mutations ([RFC 6902](https://www.rfc-editor.org/rfc/rfc6902)).
4. **JSON Schema 2020-12** for persisted IR/contract validation and **RFC 8785 JCS** for hashes, signatures, cache keys, and reproducible snapshots; JCS canonicalizes the JSON representation, whereas JSON Schema supplies vocabulary/version declarations ([JSON Schema 2020-12](https://json-schema.org/draft/2020-12), [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)).
5. **UCUM codes and canonical values at the typed host boundary**, not ad-hoc unit arithmetic inside the expression language. UCUM defines an unambiguous, machine-processable system of units and explicitly distinguishes syntax from quantity semantics ([UCUM specification](https://ucum.org/ucum)).
6. Borrow **SCXML run-to-completion/microstep terminology** and **IEC 61499 event/data-port visual precedents**, but do not persist either format as Litehouse's source of truth ([SCXML transition processing](https://www.w3.org/TR/scxml/#SelectingTransitions), [IEC 61499-1 public abstract](https://webstore.iec.ch/en/publication/5506), [Eclipse 4diac IEC 61499 introduction](https://eclipse.dev/4diac/doc/intro/iec61499.html)).

No candidate directly supplies all of Litehouse's required semantics. Workflow/statechart standards couple planning to execution; decision and expression languages omit event lifecycle and time; rule interchange formats are too large or weakly implemented for the Rust/browser target. A small owned IR is therefore not needless invention: it is the boundary that makes purity, exact-major capability typing, effect receipts, bounded execution, and graph identity normative.

## Required Litehouse semantic profile

The IR should make the following rules normative:

- A rule invocation receives an immutable `pre_state`, one normalized CloudEvent, an explicit clock snapshot, and declared capability snapshots. Expressions cannot perform I/O or read ambient time.
- Evaluation returns either a typed plan or a typed `false | unknown | error` outcome. It never calls a device, waits, retries, emits an event, or mutates stored state.
- A plan contains (a) desired-state operations, (b) separately typed effect intents, (c) assumptions/preconditions, and (d) provenance. Executors may accept, reject, partially realize, or ambiguously time out an intent. Every attempt produces a receipt event; receipts, not optimistic mutation, reconcile observed state.
- `unknown` means required information is absent or indeterminate; `error` means an invalid rule, contract, unit conversion, bound violation, or evaluator failure. Neither is truthy. Both are visible in simulation and traces.
- Delay, debounce, throttle, windows, parallel joins, and retry are graph/runtime nodes with explicit durable state. They are not CEL helper functions. Retry applies to effect execution and records every attempt; it must not silently re-run pure planning against a changed state.
- Parallel branches plan from the same immutable snapshot. Their plans are merged using declared conflict policy and stable node/edge order. Conflicting writes without an explicit merge rule are errors.
- Persist stable node and edge IDs, source/target ports, node kind/version, exact-major contract references, layout as non-semantic metadata, and a separately canonicalized semantic document. React Flow becomes a projection/editor, not the semantic model.
- A capability hook declares input/output schemas, purity, determinism, cost, exact major, unit dimensions, and supported targets. Major-version mismatch or incompatible UCUM dimension is a compile error.
- Bounds are part of the artifact/profile: maximum source and checked-AST size, nesting, collection/cardinality, comprehension cost, output/patch size, extension cost, and wall-clock cancellation. Reject profiles that cannot account for a host extension's cost.

This gives a direct simulation seam: evaluate from a recorded snapshot without adapters, inspect the proposed patch/intents, and then replay executor receipts separately. A trace should record artifact digest, node/edge ID, input snapshot/event digest, checked expression digest, result/unknown/error, cost, plan digest, dispatch attempt, receipt, and reconciliation result.

### Evidence behind the table

#### RIF-PRD

RIF-PRD is explicitly a standard XML serialization for production rule languages and defines condition matching, action blocks, operational rule-set semantics, conflict resolution, halting, imports, conformance, and XML syntax. Its atomic actions include `Assert`, `Retract`, `Modify`, and `Execute`; action blocks are sequential, and externally defined actions are part of execution. Those are strong production-rule interchange semantics but the opposite of a narrow pure-plan boundary ([W3C RIF-PRD Recommendation](https://www.w3.org/TR/rif-prd/), especially [actions](https://www.w3.org/TR/rif-prd/#Actions), [operational semantics](https://www.w3.org/TR/rif-prd/#Operational_semantics_of_rules_and_rule_sets), and [conformance/interoperability](https://www.w3.org/TR/rif-prd/#Conformance_and_interoperability)). RIF's own goal is interchange between rule systems, not compact browser execution or graph editing.

#### Reaction RuleML

The official RuleML repository calls `eca.xsd` the “Event-Condition-Action Rule (ECA) dialect of Reaction RuleML,” version 1.02, and includes event, action, time, interval, spatial-temporal, and algebra modules ([ECA schema](https://github.com/RuleML/reaction-ruleml/blob/1.02/xsd/eca.xsd), [official repository](https://github.com/RuleML/reaction-ruleml/tree/1.02)). The same schema declares RuleML Inc. copyright and the custom RuleML Specification License rather than an OSI licence or an SDO publication ([schema licence declaration](https://github.com/RuleML/reaction-ruleml/blob/1.02/xsd/eca.xsd)). This is a broad community interchange vocabulary, not evidence of a compact conforming runtime. Its semantic breadth would force Litehouse to specify a restrictive dialect almost as large as the owned IR it replaces.

#### DMN 1.5 and FEEL

OMG identifies DMN 1.5 as a formal specification, published August 2024, with normative PDF, XSD, XMI, and Diagram Interchange artifacts ([OMG DMN 1.5 inventory](https://www.omg.org/spec/DMN/1.5/About-DMN), [normative PDF](https://www.omg.org/spec/DMN/1.5/PDF), [normative model XSD](https://www.omg.org/spec/DMN/20230324/DMN15.xsd), [normative DI XSD](https://www.omg.org/spec/DMN/20230324/DMNDI15.xsd)). The PDF defines FEEL as side-effect-free, with simple values/contexts and three-valued `true`, `false`, `null`, and defines DRG/DRD, boxed expressions, decision tables, and decision services. That makes DMN the best standardized *decision diagram* in the comparison, but it deliberately complements process standards rather than defining triggers, retries, durable timers, or ambiguous effects. Mapping a DMN DRG into a React Flow subgraph is reasonable; forcing the complete automation into DMN is not.

#### SCXML

SCXML standardizes state, transition, parallel regions, history, events, executable content, datamodel mutation, delayed `send`, `cancel`, and service `invoke`; it also defines deterministic transition selection and microstep/macrostep processing ([W3C SCXML Recommendation](https://www.w3.org/TR/scxml/), [core constructs](https://www.w3.org/TR/scxml/#CoreIntroduction), [transition selection/execution](https://www.w3.org/TR/scxml/#SelectingTransitions), [send](https://www.w3.org/TR/scxml/#send), [invoke](https://www.w3.org/TR/scxml/#invoke), [datamodels](https://www.w3.org/TR/scxml/#DataModels)). The normative datamodel choices are null and ECMAScript, while executable content is extensible, so interoperable static types and sandbox behavior are not supplied. SCXML is compelling for a controller's internal lifecycle, but making device calls in `invoke`/`send` prevents the required universal plan/effect split unless Litehouse defines a large restrictive profile.

#### CNCF Serverless Workflow 1.0

Version 1.0.0 defines a versioned YAML/JSON workflow document and tasks including call, emit, fork, listen, run, set, switch, try, and wait, with schedules, event correlation, timeouts, retries, lifecycle events, and extensions ([1.0.0 DSL](https://github.com/open-workflow-specification/specification/blob/v1.0.0/dsl.md), [1.0.0 reference](https://github.com/open-workflow-specification/specification/blob/v1.0.0/dsl-reference.md), [1.0.0 schema](https://github.com/open-workflow-specification/specification/blob/v1.0.0/schema/workflow.yaml)). Version 1.0 requires jq as the default runtime expression language and permits alternatives, which weakens portable typing and bounded evaluation ([runtime expressions](https://github.com/open-workflow-specification/specification/blob/v1.0.0/dsl.md#runtime-expressions)). The project and specification are Apache-2.0 ([repository](https://github.com/open-workflow-specification/specification)); the official Rust SDK's published tags remain alpha6 variants and its repository describes SDK support rather than a browser execution engine ([Rust SDK](https://github.com/open-workflow-specification/sdk-rust), [Rust SDK releases](https://github.com/open-workflow-specification/sdk-rust/tags)). It solves cloud service orchestration, a materially larger and more effectful problem.

#### CloudEvents, CESQL, and Subscriptions

CloudEvents 1.0.2 defines required context attributes (`id`, `source`, `specversion`, `type`) and optional attributes while treating event `data` according to its declared content type/schema; it does not define automation semantics ([CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)). CESQL 1.0.0 is a total, pure, referentially transparent predicate language over a valid CloudEvent, with a small type system and separate error set. It explicitly excludes the polymorphic `data` field; in subscription filtering, non-Boolean results or any error fail closed ([CESQL 1.0.0](https://github.com/cloudevents/spec/blob/cesql%40v1.0.0/cesql/spec.md), [CESQL TCK](https://github.com/cloudevents/spec/tree/cesql%40v1.0.0/cesql/cesql_tck)). The Subscriptions API remains marked `Version 0.1-wip`, so it is not a stable persistence or control API for Litehouse ([Subscriptions specification](https://github.com/cloudevents/spec/blob/main/subscriptions/spec.md)).

#### IEC 61499 precedent

The public IEC abstract says IEC 61499-1 defines a generic, domain-independent, extensible architecture for distributed industrial measurement/control, expressed through implementable reference models, textual syntax, and graphical representations ([IEC 61499-1:2012 public record](https://webstore.iec.ch/en/publication/5506)). The public Eclipse 4diac documentation illustrates function blocks with event/data interfaces, algorithms, execution-control charts, composite function-block networks, applications, devices, and resources ([IEC 61499 introduction](https://eclipse.dev/4diac/doc/intro/iec61499.html)). Eclipse's official IDE and FORTE repositories are Java and C++ respectively and EPL-2.0 licensed ([4diac IDE](https://github.com/eclipse-4diac/4diac-ide), [4diac FORTE](https://github.com/eclipse-4diac/4diac-forte)). Only these publicly documented precedents should be relied upon without purchasing the standard; Litehouse should not claim IEC conformance.

#### CEL

CEL's specification states that evaluation is linear-time, mutation-free, non-Turing-complete, side-effect-free, and terminating; it supports typed host context and extension functions, and recommends persisting its canonical checked AST protobuf ([CEL overview](https://github.com/cel-expr/cel-spec/blob/master/README.md)). The language is strongly typed at runtime and gradually typed through an optional checker; it defines error and unknown propagation rather than collapsing both to false ([CEL language definition](https://github.com/cel-expr/cel-spec/blob/master/doc/langdef.md), [CEL type-checking introduction](https://github.com/cel-expr/cel-spec/blob/master/doc/intro.md)). The independent `cel-rust` implementation is MIT, embeddable, and supports host functions, but its README does not claim full checker/TCK or browser-Wasm conformance ([cel-rust](https://github.com/cel-rust/cel-rust), [licence](https://github.com/cel-rust/cel-rust/blob/master/LICENSE)). Litehouse therefore needs a pinned-version conformance spike, not an assumption of drop-in parity.

#### jq and jaq

jq is a filter language that maps one JSON input to zero, one, or many outputs and offers assignments, generators, `try/catch`, recursion, `while`, and `repeat` ([jq 1.8 manual](https://jqlang.org/manual/)). That transformation power is attractive but its dynamic cardinality and recursion complicate a total, bounded, typed planner. jaq is an MIT Rust jq-compatible library and demonstrates browser use through its playground, but its official security section explicitly says it has no resource-exhaustion countermeasures and may take unlimited time, memory, or stack; recursive examples can overflow the stack ([jaq README/security](https://github.com/01mf02/jaq#security), [jaq core](https://github.com/01mf02/jaq/tree/main/jaq-core), [MIT licence](https://github.com/01mf02/jaq/blob/main/LICENSE-MIT)). That disqualifies unrestricted jaq for untrusted household rules despite good transformation ergonomics.

#### Rego, OPA Wasm, and Regorus

Rego is OPA's declarative policy language for structured data; absent rule results are `undefined`, the compiler has strict checks, and JSON Schema can improve checks, but it remains a policy DSL rather than an event workflow standard ([Rego policy language](https://www.openpolicyagent.org/docs/policy-language)). OPA can compile entrypoints to Wasm and provides a JavaScript SDK; some built-ins, including `http.send`, require host implementation, so sandbox determinism depends on the enabled builtin set ([OPA Wasm](https://www.openpolicyagent.org/docs/wasm), [OPA Apache-2.0 source](https://github.com/open-policy-agent/opa)). Regorus provides Rust/no-std and JavaScript/Wasm bindings and reports mostly matching an OPA suite; its own measurements are 6.3 MB for a stripped default example and 1.9 MB without default features ([Regorus README](https://github.com/microsoft/regorus), [Cargo features/licensing](https://github.com/microsoft/regorus/blob/main/Cargo.toml)). This is credible implementation maturity, but larger and less graph-friendly than CEL plus a typed plan IR.

#### Starlark

The canonical Starlark specification defines a deterministic Python-like configuration language with no ambient application functions unless the host supplies them ([Starlark specification](https://github.com/bazelbuild/starlark/blob/master/spec.md)). Meta's Apache-2.0 Rust implementation is used by Buck2 and offers host interoperability, optional runtime-checked types, linting, LSP, fuzzing, and a wasm-target source module. Its README also explicitly says API stability and minimal dependencies are non-goals and lists spec deviations including recursion and top-level `for` ([starlark-rust README](https://github.com/facebook/starlark-rust), [Cargo manifest](https://github.com/facebook/starlark-rust/blob/main/starlark/Cargo.toml), [licence](https://github.com/facebook/starlark-rust/blob/main/LICENSE)). It is a strong configuration engine but too script-shaped and heavy for a reviewable automation graph.

## Graph, persistence, and interoperability design

A React Flow projection should be nearly lossless because semantic graph identity is persisted independently of layout:

- **Trigger ports:** CloudEvent envelope type/source/subject/schema constraints; optional CESQL only for broker-portable context filtering.
- **Condition/derive nodes:** pinned CEL source plus checked AST digest, declared input/output types, and cost ceiling.
- **State nodes:** immutable snapshot selectors and typed desired-state patch builders.
- **Effect nodes:** exact-major Litehouse capability intent; UCUM-coded quantity plus dimension; idempotency and reconciliation policy.
- **Control nodes:** explicit delay/until, debounce/throttle/window state, deterministic fork/join, and executor retry policy.
- **Receipt/reconcile nodes:** success, rejected, timed-out/ambiguous, observed-state and compensation paths.

Persist source for review, a checked/canonical form for execution, and migration metadata. Canonicalization must exclude editor layout from the semantic digest but preserve layout in the containing artifact. A semantic version identifies the Litehouse IR; each node kind and capability contract has its own exact-major reference. Migrations create a new artifact version rather than silently rewriting the signed/canonical document. JSON Schema validates shape; JCS canonicalizes the digestable JSON; JSON Patch supplies interoperable state-delta syntax where appropriate ([JSON Schema 2020-12](https://json-schema.org/draft/2020-12), [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785), [RFC 6902](https://www.rfc-editor.org/rfc/rfc6902)).

Standards interoperability should be explicit and asymmetric:

- Import/export CloudEvents without semantic loss at event boundaries.
- Import a constrained DMN decision as a pure decision subgraph, with validation that it has no unsupported external functions.
- Export traces and receipts as CloudEvents.
- Optionally map simple SCXML statecharts or Serverless Workflow definitions into Litehouse IR, but mark constructs that cross the pure/effect boundary as non-round-trippable.
- Do not advertise RIF-PRD, Reaction RuleML, SCXML, DMN, Serverless Workflow, or IEC 61499 conformance unless the corresponding normative conformance suite/profile is actually implemented.

## What not to adopt

1. **Do not adopt RIF-PRD or Reaction RuleML as the persisted rule format.** RIF is action-oriented XML production-rule interchange; Reaction RuleML is broader, community-maintained, custom-licensed, and lacks the required Rust/browser runtime evidence.
2. **Do not use SCXML as the universal automation model.** It is excellent for lifecycle statecharts but its pluggable datamodel and effectful executable content make type safety and pure planning profile-specific.
3. **Do not use DMN as an event/workflow language.** Use it only for optional pure decision interoperability.
4. **Do not adopt Serverless Workflow 1.0 as the embedded engine.** It is a cloud orchestration DSL, makes effectful calls/runs first-class, defaults to jq, and its official Rust support is still alpha-tagged.
5. **Do not treat CloudEvents Subscriptions 0.1-wip as a stable control-plane contract, and do not use CESQL for payload rules.** CESQL explicitly omits `data`.
6. **Do not expose unrestricted jq/jaq.** jaq's own security documentation rejects bounded-resource assumptions.
7. **Do not adopt Rego as the core rule language solely because Wasm exists.** It is a capable policy engine, but undefined/set/module semantics and footprint add complexity without supplying time, graph, or effects.
8. **Do not adopt Starlark for user automations.** Scripts project poorly into a graph, and the Rust implementation intentionally prioritizes power over minimal size/stable embedding API.
9. **Do not claim physical effects are atomic state patches.** A desired post-state is a plan; adapters produce receipts, and timeout is an ambiguous outcome until reconciled.
10. **Do not make CEL host extensions an escape hatch.** No ambient clock, randomness, filesystem/network, adapter call, unmetered collection, or version-floating capability is allowed in the strict profile.

## Validation gates before implementation commitment

Evidence is sufficient for the architecture decision, but these implementation measurements remain required before pinning libraries:

1. Build a representative strict-CEL corpus covering typed capability inputs, `unknown` versus `error`, UCUM host functions, and structured plan fragments; run the upstream CEL conformance corpus applicable to the selected feature set.
2. Compare the pinned Rust CEL candidates for checker coverage, unknown/error fidelity, deterministic cost accounting, custom-function typing, `wasm32-unknown-unknown` support, licence, and maintenance. The current `cel-rust` README alone is not sufficient proof of full CEL conformance ([CEL spec](https://github.com/cel-expr/cel-spec), [cel-rust](https://github.com/cel-rust/cel-rust)).
3. Measure release Wasm bytes (raw and compressed), parse/check/evaluate latency, peak memory, cancellation, and adversarial cost. No reviewed standard gives a transferable binary-size guarantee.
4. Round-trip representative graphs through canonical JSON, JSON Schema validation, JCS hashing, and React Flow projection; prove layout changes do not change semantic digests.
5. Simulate retries, concurrent conflicting plans, stale `test` preconditions, timeouts with unknown physical outcome, late receipts, exact-major mismatch, and incompatible UCUM dimensions.

The fallback if no Rust CEL implementation passes these gates is **not** jq, Rego, or Starlark. It is a deliberately smaller owned typed expression AST implementing only literals, field access, Boolean/comparison/arithmetic operators, bounded collection predicates, explicit error/unknown, and whitelisted pure functions, while retaining CEL syntax/interchange only where faithfully supported.
